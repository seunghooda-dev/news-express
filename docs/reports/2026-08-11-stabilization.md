## 2. 가장 큰 것 — 0.1MB 파일이 컨테이너를 넘긴다

```
poster.png   파일 0.1MB (6000x6000 평면)  →  피크 614.7MB
```

**바이트 상한(12MB)은 아무 방어도 못 한다.** PNG 압축률에 한계가 없어서 평면 스캔
공고는 0.1MB가 36MP로 펼쳐진다 — 지자체가 올리는 공고문이 정확히 이 모양이다.
게다가 알파가 있으면 캔버스·RGBA 사본·붙이기로 **원본이 3벌 동시에** 산다.

세 가지를 고쳤다.

1. 펼치기 전 **화소 가드**(미리보기 16MP · 카드 12MP). `draft()` **뒤** 크기로 재므로
   JPEG는 이미 줄어든 값이고, 위험한 경우만 정확히 걸린다.
2. **줄인 뒤에 알파를 합성**한다. 480px로 줄이고 나면 사본이 무의미해진다.
3. `draft()` 목표 크기를 **가로세로비에 맞춘다**. 정사각 상자를 주면 `draft`가
   "요청보다 작아지지 않는" 최대 축소만 고르므로, 6000×4000에 (2160,2160)을 주면
   1/2인 3000×2000의 세로가 2160보다 작아 **1/1이 선택된다** — 24MP가 그대로 펼쳐진다.

| 입력 | 전 | 후 |
|---|---|---|
| 36MP 평면 PNG (0.1MB) | 614.7MB | **65.1MB** |
| 25MP PNG (75MB) | 291.2MB | 100.2MB |
| 9MP RGBA PNG | 236.7MB | 174.5MB |
| 24MP JPEG 3:2 | 90.6MB | 88.6MB (영향 없음) |

측정은 자식 프로세스의 **피크 워킹셋**으로 했다. `tracemalloc`은 파이썬 할당만
보므로 Pillow의 C 버퍼가 안 잡힌다 — 처음에 그걸로 재서 "0.1MB"라는 무의미한 값을
얻었다가 방법을 바꿨다.

## 3. 크롤 표면 — robots가 로그인 뒤에 있었다

```
/robots.txt   302 -> /login?next=/robots.txt
/sitemap.xml  302 -> /login?next=/sitemap.xml
```

크롤러는 규칙을 못 읽으면 "제한 없음"으로 간주한다. 그런데 열려 있는 면이 넓다.

- 목록 65KB · 초안 상세 15KB × 1700여 건 · **원본 첨부 이미지**가 전부 익명 200
- `?q=`·`?page=`는 아무 값이나 받아 200을 돌려준다(`?page=999`도 `?page=abc`도 같은
  65KB) — 서로 다른 URL이 무한히 생기고 하나하나가 Postgres 조회를 부른다

카드뉴스와 첫 화면은 **일부러 남겼다** — 카톡·밴드 미리보기가 확산 경로다.

## 4. DB 전송량 (무료 한도 초과, 유예 2026-09-03)

`source_collection_runs`를 네 곳이 각자 `WHERE`도 `LIMIT`도 없이 전량 스캔하고 있었다.
그중 하나는 **공개 첫 화면이 매 요청마다** 부른다. 이 테이블은 활성 27개 × 매시라
하루 650건 넘게 늘고 **DELETE가 어디에도 없다.**

소비하는 쪽은 소스별로 **첫 성공에서 멈추고** 판정 문턱이 3회다 — 전량이 필요했던
적이 없다. 윈도우 함수로 소스별 최근 N건만 뽑도록 하나로 모았다.

상한은 처음에 10으로 잡았다가 **50으로 올렸다**(§9). 판정에는 3이면 충분하지만
그 횟수가 화면 문구("연속 실패 N회")와 복구 우선순위 정렬에도 쓰여서, 10이면 3일
죽은 곳과 10시간 죽은 곳이 같은 값으로 붙는다. 매시 수집이라 50은 이틀치이고
27개 × 50 = 1350행이라 전송량은 여전히 무시할 만하다.

공개 첫 화면의 `_attention_count_for_dashboard`도 **숫자 하나를 세려고** 대기 초안
본문을 통째로 옮기고 있었다(행당 4KB 남짓). `review_flags`가 본문을 쓰는 곳은 맨 앞이
제목으로 시작하는지 한 줄뿐이라 앞 400자만 가져온다. 앞 5자면 판정이 달라지고
20자부터 전량과 같아지는 것을 실측으로 확인했다.

**프로덕션 행 수는 못 쟀다** — `DATABASE_URL`이 Render 대시보드에만 있다.

이미 있다. 백업이 이 테이블을 통째로 담으므로 백업 크기도 같이 자란다.

**증가 속도를 실측했다**(같은 스키마에 2000행을 넣어 잰 값, 인덱스 포함 행당 385B).

처음에 이 항목을 급한 것처럼 적었는데 **수치를 재고 나서 정정한다.** 재기 전에

## 5. 헛돌던 테스트

카드뉴스 POST 5종의 로그인 검증이 CSRF에 가려 있었다. 재현:

| 경로 | CSRF 켜짐(종전 테스트) | CSRF 꺼짐(인증 층 도달) |
|---|---|---|
| `/card-news/build` 외 4종 | **400** | 302 `/login?next=…` |

`protect_state_changing_requests`가 `require_admin_login`보다 먼저 등록돼, 토큰 없는
POST는 인증 검사 **앞에서** 끊긴다. `in {302, 400}`이 400만 보고 통과해
**인증을 통째로 지워도 초록**이었다.

conftest에도 같은 계열의 함정이 장전돼 있었다 — `AUTH_DISABLED`만 `delenv`라
`.env`가 되살려서, "인증 켜고 확인"하려고 `AUTH_REQUIRED=1`만 설정한 테스트가 조용히
인증이 꺼진 채 통과한다. 바로 위 줄들이 이미 "삭제 대신 빈 값" 방식이고 이유까지
주석에 있는데 그 줄만 달랐다.

## 6. 권한 메타테스트

라우트를 하나씩 세는 대신 `url_map`을 돈다. 실측: POST 28개(로그인 15·운영 9·면제 4),
GET 24개(공개 12·로그인 5·운영 4·면제 3). 이 중 **로그인 요구가 검증되던 POST는 4개**뿐이었다.

넷을 넣었다 — ①POST 전수 로그인 요구 ②운영 라우트가 **관리자 로그인만으로는** 안 열림
③공개 읽기 전수가 안 닫힘 ④**면제 목록 스냅샷**.

④가 핵심이다. ①~③은 라우트를 돌며 검사하므로 누가 엔드포인트를 면제 목록에 넣으면
검사 대상에서 빠져 조용히 통과한다. `card_news_delete`를 면제에 주입해 실증했다 —
개수 단언에만 걸렸고, 라우트를 하나 더 추가하면서 면제했다면 그마저 통과했을 것이다.

## 8. 작업 방식에서 지킨 것

**감사 결과를 받은 대로 믿지 않았다.** 게이트에 실패 2건이 떴을 때 바로 고치지 않고
①작업 트리를 stash → 여전히 실패(내 미커밋 변경이 원인 아님) ②conftest를 옛 방식으로
되돌림 → 하나는 통과·하나는 실패(두 실패의 성격이 다름) ③캐시 키를 직접 찍어 관찰
순서로 갈랐다. 결론은 **운영 화면 캐시가 원리적으로 못 맞는 구조**였다.

**기존 테스트가 내 실수를 잡았다.** 화소 가드를 넣자 정상적인 3:2 대형 JPEG가
걸러졌는데, 그 실패를 파다가 `draft()` 호출이 정사각 상자를 넘겨 축소를 아예 못 하고
있었다는 더 깊은 결함이 드러났다.

**메타테스트의 이빨을 실증했다.** 보호를 실제로 빼 보고 잡히는지 확인했고, 처음 시도는
`PUBLIC_READ_ENDPOINTS`가 GET에만 적용돼 보호가 안 풀리는 잘못된 주입이었다.

## 9. 안정화 자체를 다시 검토했다 — 결함 5건이 더 나왔다

12커밋을 무인으로 넣은 뒤, **그 변경만 대상으로** 독립 검토를 붙였다. 전부 재현했다.

| 결함 | 무엇이 어긋났나 |
|---|---|
| **잘못된 날짜가 발행 중인 세트를 파괴** | 검증이 DB 쓰기 **뒤**에 있었다 |
| robots.txt가 히트마다 DB를 열고 방문 기록 INSERT | 면제 집합이 셋인데 하나에만 넣었다 |
| 팔레트 이미지가 NEAREST로 강등(고유색 81 → **2**) | 축소를 알파 합성 앞으로 옮긴 부작용 |
| 안내가 첨부 수를 잘못 말함 | 시도 수가 아니라 `is_image` 전량을 셌다 |
| 연속 실패 횟수가 10에서 잘림 | 판정(문턱 3)만 보고 표시·정렬 용도를 놓쳤다 |
| **주민 첫 화면이 빈 채로 나감** | 날짜 목록은 행 기준, 화면은 그림 기준 |
| **공유 링크가 다른 날 뉴스를 보여 줌** | 발행이 내려가면 조용히 최신 날짜로 갈아 끼웠다 |

첫째가 가장 나쁘다. 재현:

```
발행 상태  publish_date='2026-08-09' status='published'
잘못된 날짜로 다시 만들기
결과       publish_date='2026/08/09' status='draft' published_at=''
```

`save_card_news_set`은 draft_id 기준 UPSERT라 행이 먼저 덮이고(날짜가 바뀌고 발행이
내려가고) 그다음에 던진다. 이미지는 옛 경로에 고아로 남고 롤백이 없다.
**"동작하지만 지저분"이었던 것을 "부분 실패 + 상태 파괴"로 바꿔 놓은 셈이다.**

뒤의 둘은 **주민 화면에 직접 나타난다.**

```
그림 삭제 후 · 최신 표지 False · 옛 표지 False · 빈 안내 True   <- 빈 랜딩
발행 내린 뒤 · 공유 링크 → 옛 기사 노출 True                    <- 엉뚱한 날
```

기본 랜딩은 그림이 있는 첫 날짜로 내려가고, 요청한 날짜는 그대로 지킨다. 두 동작이
반대 방향으로 보이지만 기준은 하나다 — **방문자가 날짜를 직접 골랐으면 그 답을
지키고, 안 골랐으면 볼 것을 찾아 준다.**

그리고 게이트가 한 번 더 잡았다 — 안내 문구를 바꾸고 그 테스트를 안 고쳐 빨간
트리가 났다. 밤새 지적해 온 "짝이 안 맞게 된 쪽"을 스스로 또 만들었고 커밋 전에 걸렸다.

**교훈**: 안정화 작업 자체가 새 결함을 만든다. 무인으로 12건을 넣었으면 그 12건에
다시 검토를 붙여야 한다. 오늘 그것이 실제로 심각 결함 하나를 프로덕션 직전에 잡았다.

## 10. 배포 중 `주의` 신호 — 규명 완료, 정상 동작이다

배치 중 `safe_deploy` 로그에 `(서비스 주의)`가 세 번 찍혀 그때마다 확인했다.
사슬은 이렇다.

1. `_deployment_version_report`가 **실행 중 커밋 ≠ 원격 최신 커밋**이면
   `배포 필요 · warning`을 낸다(문서만 바뀐 경우는 `ok`로 걸러 낸다).
2. 그것이 `service_status_issues`로 올라가 라벨이 `주의`가 된다.
3. `safe_deploy.py`는 **푸시하기 직전에** 그 라벨을 읽는다.

즉 앞선 푸시가 아직 빌드 중이면 다음 푸시 로그에는 반드시 `주의`가 찍힌다.
밤새 23번 연달아 푸시했으므로 **내가 만든 신호**였고, 시스템은 "배포 대기 중"이라고
정확히 말하고 있었다. **쫓을 것이 아니다** — 다음 사람이 같은 로그를 보고 다시
파지 않도록 남긴다.

같은 이유로 배포 직후 첫 헬스 요청이 502·`JSONDecodeError`인 것도 재기동 창이다.
20~25초 뒤 정상으로 돌아온다(실측).

### `주의`의 두 번째 원인 — 회차 직후 30초 창 (정상 운영 중 반복)

배포와 무관하게도 뜬다. `auto_collector_timing`이 `overdue`가 되는 창이다.

```
09:19:29  주의  overdue=True   next_run_at 09:00  ← 회차가 방금 끝났는데 갱신 전
09:20:00  정상  overdue=False  next_run_at 10:00  ← 30초 만에 자기 정정
```

수집 회차가 **약 17분** 걸리고(09:03~09:17, 10:03~10:20 실측), 다음 슬롯 계산이
회차 종료 뒤에 오므로 그 사이가 "지났습니다"로 잡힌다. 설계대로 스스로 풀린다.

**다만 여유폭을 알아 둘 것** — 이 경고는 회차 소요 시간에 직접 걸린다. 17분이면
무해하지만 60분에 가까워지면 진짜 신호가 된다. 회차가 길어지는 변경(소스 추가,
타임아웃 상향)을 할 때 이 값을 함께 본다.

### 회차 뒤 메모리는 누적이 아니라 평탄화다 (실측)

| 시점 | 메모리 | 증가 |
|---|---|---|
| 회차 전 | 69MB | — |
| 09시 회차 후 | 167MB | +98 |
| 10시 회차 후 | 189.5MB | +22 |
| 17:30 (7시간 뒤) | 230.6MB | +41 |
| **18시 회차 후** | **230.7MB** | **+0.1** |

**약 230MB에서 멈춘다.** `2026-08-05` 리포트의 "236MB 고정"과 같은 값이고 512MB
한도에 여유가 있다.

판정 과정을 남겨 둔다 — 09시 표본 하나만 보고 "회차마다 100MB가 안 돌아온다"고
쓸 뻔했고, 10시에 +22로 꺾이는 것을 보고 "평탄화"라고 했다가, 17시에 +41이 더 붙은
것을 보고 **판정을 유보로 되돌렸다.** 마지막에 회차를 하나 더 통과시키니 +0.1이라
확정됐다. **한두 표본으로 추세를 말하면 없는 문제를 쫓거나 있는 문제를 놓친다.**

## 12. 컨테이너는 UTC인데 세 곳이 그것을 몰랐다 (2026-08-12)

내보내기(`exporter.py`)는 운영자 일과의 **마지막 단계**인데 테스트가 0건이라 감사 대상으로
골랐다. 첫 의심(`approved_time` 별칭이 없어 정렬이 틀릴 것)은 **틀렸다** — 실제로 확인하니
`approved_drafts`가 `COALESCE(ad.updated_at, ad.created_at) AS approved_time`으로 별칭을 준다.
대신 그 옆에서 다른 것이 나왔다.

### 실체

```
exporter.py:22          내보내기 파일명       datetime.now()   <- naive
backup.py:57            백업 파일명           datetime.now()   <- naive
cardnews_service.py:75  publish_date 기본값   datetime.now()   <- naive
```

`render.yaml`에 TZ 설정이 없어 **컨테이너는 UTC로 돈다.** 앱은 `web.py`에서만
`datetime.now(LOCAL_TZ)`를 37곳에서 쓰고 있었으니 KST가 규약이고 이 셋만 예외였다.

셋 다 사용자에게 보이는 값이고, **세 번째는 기능 버그다.** 한국 시각 00~09시에 카드뉴스를
만들면 `publish_date`가 **어제 날짜**로 잡혀 주민 화면에서 하루 밀려 묶인다.

### 고치기 전에 확인한 것

백업 파일명을 바꾸면 **보관 정리가 흔들릴 수 있다**고 보고 먼저 봤다.
`_backup_files_newest_first`는 `key=lambda path: path.stat().st_mtime`으로 정렬한다 —
파일명이 아니라 mtime이다. 이름을 바꿔도 지워지는 순서는 그대로다.

### 테스트 — 이 머신에서는 헛도는 테스트가 나오기 쉬웠다

개발 PC가 KST라 `naive now()`와 `now(LOCAL_TZ)`가 **같은 값을 낸다.** "파일명이 지금
시각과 맞는가"로 짜면 고치기 전 코드도 통과한다. 그래서 **모듈의 `LOCAL_TZ`를 UTC-11로
바꿔치기하고 결과가 그것을 따라가는지** 본다 — 어느 시간대의 머신에서도 판별된다.

이빨 검사(고치기 전 코드로 되돌려 실행).

```
naive 복원 후   test_export_filename_uses_korean_time...   FAILED  ('20260812_0224')
                test_backup_filename_uses_korean_time      FAILED
                test_publish_date_default_follows_korean_time  FAILED
수정 복원 후    3건 전부 통과
```

`exporter.py`는 테스트가 0건이었으므로 시간대 외에 **재내보내기 방지**(두 번째 호출이
0건)와 **엑셀 한글 깨짐 방지**(UTF-8 BOM)도 같이 덮었다.

### 같은 계열을 넓혀 확인한 것

| 확인 | 결과 |
|---|---|
| `src/`·`scripts/`의 다른 naive `now()`·`utcnow()`·`today()` | **0건** — 세 곳이 전부였다 |
| `_approved_local_date`의 naive 분기가 실제로 도는가 | **안 돈다.** `_now()`가 `datetime.now(timezone.utc).isoformat()`로 aware를 저장하고, 스키마에 `CURRENT_TIMESTAMP` 기본값이 **하나도 없다**. 모든 행이 aware라 `astimezone` 분기만 탄다 |
| "오늘 승인 기사" 내보내기 범위 | 위 때문에 **정확하다** — 의심했으나 버그가 아니었다 |

### 확인 결과 고치지 않기로 한 것

| 항목 | 판단 |
|---|---|
| CSV 수식 주입(`=`·`+`·`@`로 시작하는 셀) | **기각.** 내용이 지자체 보도자료와 Gemini 한국어 산문이라 해당 문자로 시작하는 경우가 사실상 없다. 흔한 `- ` 불릿은 엑셀에서 실행이 아니라 `#NAME?` 오류로 끝난다. 반대로 `'` 접두 방어는 운영자가 보는 제목을 실제로 더럽힌다. 로컬 DB는 비어 있고 프로덕션 DB 접속 정보가 로컬에 없어 발생 빈도는 세지 못했다 — **세지 못했다는 것도 적어 둔다** |
| 0건 내보내기도 빈 파일 2개를 만든다 | 사실이다. 다만 고치려면 `export_approved`의 반환 타입을 바꿔 호출자 둘을 손대야 하는데, 얻는 것은 "빈 파일 경로를 flash에 안 띄운다"뿐이다. **운영자 일과의 마지막 단계에 그 위험을 질 값이 아니다** |

## 14. 사이트 개편 자가 진단 경로가 통째로 미검사였다 (2026-08-12)

커버리지 수치로 대상을 고르니 `web.py`를 빼고 가장 큰 미커버 덩어리가 나왔다 —
`scheduler.py` **1135~1240 약 100줄이 전부 0**이었다.

그 100줄이 하는 일은 **소스가 3회 연속 구조적 실패를 내면 홈페이지를 훑어 새 보도자료
주소 후보를 찾아 주는 것**이다. 이 프로젝트에서 실제로 반복되는 고장이 정확히
"지자체가 사이트를 개편했다"인데(강진 건), 그걸 복구하라고 만든 경로가 한 줄도
검사되지 않고 있었다.

### 같이 드러난 결합

`_consecutive_failure_counts`는 **연속** 실패만 세야 하는데, 그 정확성이 내가 이번
세션에 쓴 SQL의 `ORDER BY source_id, id DESC`에 걸려 있다. 정렬이 바뀌면 이 함수는
떨어져 있는 실패까지 연속으로 세면서 **조용히** 틀린 값을 낸다. 그 결합을 지키는
테스트가 없었다.

### 중복 함수 2개 — 하나는 이미 갈라져 있다

`scheduler.py`와 `web.py`에 같은 이름의 모듈 수준 함수가 둘 있다.

| 함수 | 상태 |
|---|---|
| `_consecutive_failure_counts` | **바이트 단위로 동일**. 그런데 테스트는 `web` 판만 부른다 — 정작 유지보수 루프가 쓰는 것은 `scheduler` 판이다 |
| `_parse_datetime` | **이미 갈라졌다.** naive 값을 `web`은 KST로, `scheduler`는 UTC로 해석한다 — 9시간 차이다 |

`_parse_datetime`이 살아 있는 버그인지 호출부 5곳을 전부 확인했다. scheduler 판은
수집 회차·상태·백업 검증 JSON·소스 헬스처럼 **내부가 `_now()`로 쓴 aware UTC**만
받는다. 사이트가 준 `published_at`(naive 한국 시각)은 web 판만 받는다. 따라서
**각자 자기 입력에 대해서는 맞고, 지금 버그는 아니다.**

고치지 않았다. **이름이 같다는 이유로 합치는 것이 바로 이 함정의 발동 조건**이고,
합치려면 두 모듈의 시간대 계약을 하나로 정해야 하는데 그건 지금 요청 범위 밖이다.
대신 갈라진 사실과 근거를 여기 남긴다.

### 테스트 — 통과가 아니라 변이로 확인했다

14건을 새로 썼고 **첫 실행에 전부 통과했다.** 그래서 믿지 않고 제품 코드에 변이를
넣어 잡히는지 봤다.

```
적발  연속 실패 문턱 3 -> 1
적발  구조적 실패 단계 필터 제거
적발  연속 판정에서 성공 끊기 무시
적발  같은 호스트 검사 무력화
적발  limit 무시
적발  홈 루트 주소 추가 안 함
```

변이 6종 전부 적발했다. **첫 시도의 변이 스크립트가 중단되며 제품 파일을 변이된 채로
남겼다** — `git diff`로 원본 복원을 확인하고서야 다음으로 넘어갔다.

덮은 행동은 이렇다. 3회 미만이면 안 긁는다(한 번 삐끗한 사이트마다 홈페이지를 긁으면
유지보수가 그 자체로 부하다) · 응답 시간 초과 같은 일시 장애는 대상이 아니다 · 실패
뒤 한 번이라도 성공했으면 연속이 아니다 · **제외된 소스는 유지보수가 몰래 다시 긁지
않는다(강진 건)** · 다른 호스트와 `javascript:` 링크는 버린다 · 홈페이지 하나가 죽어도
나머지 후보 주소는 계속 본다.

### 곁가지로 확인하고 넘어간 것

`/healthz/details`가 502를 세 번 냈다. 공개 payload가 그 주소를 안내하므로 확인했더니
30초 뒤 정상 302(로그인 요구)로 돌아왔고, 시점이 `5acbef8` 배포가 살아나는 창과
겹쳤다. Render 로그 접근이 없어 그 이상은 추측이 되므로 멈췄다. `healthCheckPath`는
이미 `/healthz`로 설정돼 있고, `buildFilter.paths` 네 경로(`src`·`config`·`scripts`·
`templates`)는 전부 실재하며 수집 소스 목록(`config/municipalities.yaml`)도 포함된다.

## 15. 정정 — 문서 커밋도 프로덕션을 재시작시키고 있었다 (2026-08-12)

§14에서 `/healthz/details` 502를 "`94f54ec`는 buildFilter에 안 걸리니 배포를 유발하지
않는다"고 적었다. **틀렸다.** 그 뒤 프로덕션 `healthz`의 `commit`이 `5acbef8`에서
`94f54ec`로 바뀌었다 — 문서와 `.gitignore`만 건드린 커밋이 실제로 배포됐다.

원인은 `render.yaml` 자신이 이미 적어 둔 사실에 있다.

> 주의: 이 서비스는 대시보드에서 생성돼 대시보드 Start Command가 우선한다.
> 여기 값만 바꿔서는 반영되지 않으므로, 실제 변경은 대시보드에서 해야 한다.

`startCommand`에 대해 적힌 이 경고가 **`buildFilter`에도 그대로 적용된다.** 블루프린트가
관리하지 않는 서비스라 `render.yaml`의 `buildFilter.paths`는 효력이 없고, 빌드 필터는
대시보드에서 걸어야 한다.

### 결과

오늘 밤 문서·테스트 전용 커밋을 여러 번 푸시했고, **그때마다 프로덕션이 다시 빌드되고
재시작했다.** 재시작 창에는 주민에게 502가 나간다(§14에서 본 그 502다). 앱 코드가
한 줄도 바뀌지 않은 커밋 때문이다.

### 처방 — 커밋 메시지로 건너뛴다

Render는 커밋 메시지에 `[skip render]` 또는 `[render skip]`이 있으면 자동 배포를
건너뛴다. 대시보드 접근 없이 지금 바로 쓸 수 있는 수단이라 이것을 규약으로 삼는다.

**적용 기준** — 아래 경로가 하나도 안 바뀐 커밋에만 붙인다.

```
src/**  config/**  scripts/**  templates/**  pyproject.toml  render.yaml
```

`git diff --name-only`로 확인하고 붙인다. 반대로 제품 경로가 하나라도 바뀌면 절대
붙이지 않는다 — 고친 것이 배포되지 않는 쪽이 훨씬 나쁘다.

**더 나은 처방은 대시보드에 빌드 필터를 거는 것**이지만 그건 사용자만 할 수 있다.
커밋 메시지 규약은 그때까지의 수단이고, 필터가 걸리면 굳이 뺄 필요도 없다.

### 이 정정을 남기는 이유

§14의 그 문장은 **render.yaml을 읽고 내린 추론**이었고, 바로 옆 줄에 그것을 반박하는
주석이 있었는데도 그랬다. 설정 파일에 적힌 값이 실제로 적용되는지는 파일이 아니라
**돌아가는 서비스에서 확인해야 한다** — `healthz`의 `commit` 필드가 그 확인 수단이었고,
실제로 그것이 나를 정정했다.

## 16. 무인 유지보수 13개 중 삭제 작업 하나가 미검사였다 (2026-08-12)

커버리지 %를 그대로 따라가지 않고 **"무인으로 돌고 · 실패해도 조용하고 · 테스트가
없는"** 것을 기준으로 골랐다. 유지보수 단계 13개를 전부 세어 봤다.

```
_recover_failed_sources_once            11
_verify_latest_backup_once               8
_discover_fallback_url_candidates_once   6
_drain_pending_queue_once                4
_deduplicate_press_releases_once         2
_create_backup_if_needed_once            2
_prune_old_backups_once                  2
_cleanup_stale_draft_failures_once       1
_prune_old_operation_events_once         1
_prune_old_card_news_once                0   <- 유일
```

**하필 0인 것이 삭제 작업이었다.** 그림과 세트 행을 함께 지우고, 사람이 보지 않는
시간에 돈다. `prune_old_dates` 자체는 덮여 있었으므로 스케줄러가 **그것을 어떤 값으로
부르는지**만 채웠다.

### 소스 복구 루프도 함께 채웠다

`scheduler.py` 691~704(소스별 예외 처리)도 0이었다. 여기서 예외가 새면 **먼저 걸린
지자체 하나 때문에 그 회차의 복구가 통째로 멈춘다** — 정작 이 루프는 깨진 소스를
되살리려고 있는 것이다. 변이 5종(예외 재전파·실패 미기록·저장 생략·스냅샷 생략·
off 스위치) 전부 적발했다.

### 변이가 안 잡힌 둘을 파고들었다

**하나는 진짜 공백이었다.** 보관 기본값 30을 아무 시험도 지키지 않았다 — 내 시험이
전부 env를 명시해서, 기본값을 1로 바꿔도 초록이었다. 그러면 프로덕션 카드뉴스가
조용히 하루치만 남는다. env 미설정 상태를 거는 시험을 추가해 막았다.

**다른 하나는 이중 방어였다.** `keep_days <= 0` 가드가 스케줄러와 `prune_old_dates`
양쪽에 있어 한쪽만 지워선 안 잡힌다. **양쪽을 다 지우면 잡히는 것까지 확인**하고서야
"동작은 고정돼 있다"고 판단했다 — 안 잡혔다는 사실만으로 시험이 무르다고 결론내면
틀린다.

### 이름이 뜻을 오해하게 하는 자리

`CARD_NEWS_KEEP_DAYS`는 **나이가 아니라 "최신 날짜 폴더 N개를 남긴다"**는 뜻이다.
폴더를 이름 역순으로 정렬해 앞의 N개만 남기므로, 전부 2020년인 폴더 세 개에
`keep_days=1`을 주면 나이 기준으로는 하나도 안 남아야 하지만 실제로는 가장 최신
하나가 남는다. **내 첫 기대값이 틀려서 알았고**, 그 사실을 시험에 명시적으로 적었다.

### 확인하고 공백이 아니라고 판단한 것

`_verify_latest_backup_once` — 이번 세션에 내가 12시간 재검증 주기(`BACKUP_REVERIFY_HOURS`)
로 바꾼 곳이라 의심했으나 `test_service.py`가 이미 덮고 있다(2238~2270).

## 17. 시간대 계약을 실행 가능한 형태로 못 박았다 (2026-08-12)

§14에서 `_parse_datetime`이 두 벌이고 naive 값을 정반대로 읽는다는 것을 기록만 하고
넘어갔다. 그 뒤 확인하니 **둘 다 테스트가 0건**이었다. 오늘 고친 시간대 결함 세 개가
전부 이런 암묵적 가정에서 나왔으므로, 제품 코드는 건드리지 않고 계약만 12건으로 고정했다.

```
scheduler._parse_datetime   naive -> UTC   (내부 _now()가 쓴 값만 받는다)
web._parse_datetime         naive -> KST   (사이트가 준 게시일도 받는다)
```

핵심은 마지막 시험이다 — **"두 파서는 의도적으로 다르다"**를 걸어 두어, 이름이 같다는
이유로 무심코 합치면 그 순간 깨지게 만들었다. 변이로 확인했다.

```
적발  scheduler 판을 KST로 통합       <- 막으려던 바로 그 실수
적발  web 판 느슨한 형식 폴백 제거
```

사이트가 실제로 보내는 모양(RSS의 RFC-2822, 지자체 게시판의 `2026.08.11 14:30`)도
함께 덮었다. **통합 자체를 금지하는 것이 아니다** — 합치려면 두 모듈의 시간대 계약을
하나로 정하고 그 결정을 남긴 뒤 이 시험을 함께 고치면 된다. 조용히 통과하는 길만 막았다.

## 19. 스텁으로 꺼져 있던 유지보수 작업 둘 (2026-08-12)

§16에서 유지보수 13개의 테스트 언급 수를 셌는데, **그 수치도 정확하지 않았다.**
`_prune_old_operation_events_once`와 `_cleanup_stale_draft_failures_once`는 각각
1건으로 잡혔지만, 그 1건은 **다른 시험이 이 작업을 꺼 두려고 만든 스텁**이었다.

```python
monkeypatch.setattr(collector, "_cleanup_stale_draft_failures_once", lambda: None)
monkeypatch.setattr(collector, "_prune_old_operation_events_once", lambda now: None)
```

실제로 실행된 적은 0번이다. **"언급 수"는 §13에서 이미 틀린 지표로 판명났는데,
§16에서 같은 지표를 다시 썼다** — 이번에는 방향이 반대로(과대평가) 틀렸다.

### 확인하고 결함이 아니라고 판단한 것

`prune_operation_events`는 `created_at < cutoff_iso`를 **문자열로** 비교한다.
시간대가 섞이면 틀릴 자리라 확인했다.

| 값 | 출처 | 형식 |
|---|---|---|
| `created_at` | `_now()` | aware UTC isoformat (`…+00:00`) |
| `cutoff` | `_run_maintenance_if_due`의 `now = datetime.now(timezone.utc)` | 같은 형식 |

**둘 다 aware UTC라 비교가 일관된다 — 결함이 아니다.** 오늘 시간대 결함을 세 개
고친 뒤라 의심했지만, 이 자리는 처음부터 맞게 돼 있었다.

### 채운 것

저장소 계층(`prune_operation_events`·`cleanup_stale_draft_generation_failures`)은
이미 덮여 있으므로, **스케줄러가 어떤 기준선으로 그것을 부르는지**만 고정했다.

```
적발  기본 보관값 180 -> 30
적발  env 무시(항상 기본값)
적발  기준선 부호 뒤집기(최근 것을 지움)
적발  0건에도 메시지
```

기본 보관값 180일은 카드뉴스의 30일과 똑같이 **아무 시험도 지키지 않고 있었다.**
운영 변경 이력은 사람이 나중에 되짚어 보는 기록이라, 여기가 조용히 짧아지면
없어진 줄도 모른다.
