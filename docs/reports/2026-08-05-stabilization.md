## 2. 발견하여 고친 것

### 2-1. OOM 원인 규명 — 누수가 아니라 미반납 (`fa8a8ee`)

`/healthz`에 노출해 둔 `process_memory_mb`로 24시간 곡선을 처음 확보했다.

```

22:14  230MB  +155MB (회차)

유휴 구간이 완전히 평평하므로 시간 비례 누수가 아니다. 회차마다 계단식으로

전형적인 모습이다. **"누수 코드 찾기"는 방향이 틀렸다.**

대응으로 `MALLOC_ARENA_MAX=2`, `MALLOC_TRIM_THRESHOLD_=65536`을 넣어 반납을
유도한다. 코드 변경이 없어 효과가 없으면 두 줄만 지우면 된다.

> **주의**: 이 서비스는 대시보드에서 생성돼 대시보드 환경변수가 `render.yaml`보다
> 우선한다. 대시보드 Environment에 같은 값을 넣어야 실제로 적용된다.

### 2-5. 백업의 `.env` 포함이 기본값이었다 (`daf0bad`)

디스크 누적을 점검하다 백업 ZIP을 열어 보니 **`.env`가 들어 있었다**. `create_backup`의
`include_env` 기본값이 `True`였다.

운영에서 이를 막는 장치는 `render.yaml`의 `NEWS_SUMMARY_BACKUP_INCLUDE_ENV=0`
한 줄뿐인데, 이 서비스는 대시보드에서 생성돼 **대시보드 설정이 우선**한다(2-1과
같은 이유). 즉 그 한 줄이 실제로 적용되는지 외부에서 확인할 수 없다. 백업은 운영
관리에서 내려받을 수 있고 `.env`에는 DB 비밀번호·Gemini 키·세션 키가 들어 있다.

**확인할 수 없는 설정에 비밀 보호를 걸어 두면 안 된다.** 기본값을 제외로 뒤집어
설정과 무관하게 안전하게 만들었다. 포함이 필요하면 `=1`로 명시적으로 켠다.

> 앞선 요약표에 "`.env` 미포함"이라고 적었던 것은 `render.yaml`만 보고 단정한
> 것으로, 근거가 부족했다. 위 내용으로 정정한다.

### 2-6. 검색의 `%`·`_`가 와일드카드로 새고 있었다 (`3aac78b`)

검색 입력을 적대적으로 찔러 보다 발견했다. 라이브에서 `q=%`, `q=_`, `q=%%%%`가
모두 **50건 전량**을 반환했다(정상 검색어 `폭염`은 46건, `목포`는 18건으로 제대로
걸러졌다).

원인은 목록 검색이 SQL `LIKE`로 돌면서 입력을 `f"%{term}%"`로 그대로 끼워 넣은
것이다. `%` → 패턴 `%%%`, `_` → `%_%`가 되어 전부 통과한다.

보도자료 본문에는 "30% 증가" 같은 표현이 흔하다. `30%`를 검색하면 패턴이
`%30%%`가 되어 "30"이 든 기사가 전부 섞여 나온다. **결과가 조용히 틀리는**
종류라 눈치채기 어렵다.

`\`·`%`·`_`를 escape하고 `ESCAPE '\'`를 붙였다. 초안 목록·원문 목록 두 곳이
같은 결함이었다. 나머지 LIKE(기간·모델·지역·IP 접두사)는 설정값이나 화이트리스트라
해당하지 않는다. 파라미터는 원래부터 바인딩돼 있어 **주입 위험은 없었고 정확도
문제**다.

> 추적 도중 "검색은 파이썬 리터럴 매칭"이라고 한 번 잘못 짚었다. `_filter_drafts_by_query`는
> 존재하지만 목록 경로가 쓰는 함수가 아니었다. LIKE 조립이 `storage.py`가 아니라
> `web.py`에 있어 첫 grep에서 놓쳤다.

### 2-7. `app.css`가 매 방문 원본까지 갔다 (`cc05bd2`)

캐시 헤더를 훑다 발견했다. Cloudflare가 동적 응답을 전부 `DYNAMIC`(미캐시)으로
흘려보내는데, `app.css`도 `no-cache`라 52KB가 페이지 진입마다 0.5 CPU 원본까지
왕복하고 있었다.

`app.css`는 이미 `?v=<커밋>`이 붙어 있고 `asset_version`은 배포마다 바뀐다.
폰트에 적용한 것과 같은 이유(2026-08-04)로 1년 캐시로 못박았다. 버전이 없는
요청은 그대로 둬서 낡은 파일이 굳지 않게 했다.

결함이라기보다 폰트 규칙과의 정합·원본 부하 감소다.

### 2-8. 디스크 상한 확인 (결함 아님, 근거 기록)

1GB 디스크에 백업·미리보기 캐시·로그가 함께 쌓인다. 각 상한을 코드로 확인했다.

- 백업: `_prune_old_backups_once`가 7개 유지 (`AUTO_BACKUP_KEEP_COUNT`)
- 미리보기 캐시: `_preview_disk_evict` 200MB
- 로그: 2MB × backup 6 = 12MB

최악 합계가 250MB 미만이라 1GB 디스크가 찰 경로는 없다. 다만 **디스크 사용량이
어디에도 노출되지 않아** 실측이 아니라 코드 상한으로만 판단했다.

## 3. 점검 중 확인한 오탐 (제품 결함 아님)

기록해 두지 않으면 다음에 같은 혼란이 반복된다.

- `/search`가 302를 반환 — 목록으로 보내는 **설계대로의 동작**. 따라가면 200에 결과가 나온다.
- 로그인이 400으로 거부 — 점검 스크립트가 **CSRF 토큰을 안 보낸** 탓.
- 운영 비밀번호가 거부 — `.env`의 **실제 해시가 우선**(`verify_operations_password`는 HASH를 먼저 본다). 로컬 점검 시 `NEWS_SUMMARY_OPERATIONS_PASSWORD_HASH=""`도 함께 비워야 한다.
- Gemini 키 미인식 — `load_environment()`를 **명시적으로 호출**해야 `.env`가 로드된다.
- 목록 항목 0건 집계 — 점검 스크립트의 **CSS 셀렉터 오류**(`.row strong` → 실제는 `a.row` 아래 `.row-content strong`).

## 3-1. 회차 전 구간 메모리 실측 (점검 마무리)

12시 회차를 20~25초 간격으로 시작부터 완주까지 관측했다.

```
회차 전     70.7MB
회차 1~9분  70.7MB  (1MB도 움직이지 않음)
완주 후     80.6MB  (+9.9MB)
```

> **이 +9.9MB는 과소평가다.** 12시 회차 도중 재배포(`e585bb5`→`85672b4`)가 끼어
> 회차가 끊겼다 다시 돌았다. 재배포 전 구간까지 포함한 별도 관측에서는
> 시작 82.1MB → 최고 122.0MB로 **회차 증가 39.9MB**였다. 두 수치를 모두 적어 둔다.
> **확정값은 3-3의 +10.0MB다** — 방해 없이 완주한 13시 회차 측정.

전날 같은 구간이 **+155MB**였다. 즉 계단식 상승의 주범은 수집 회차 자체가 아니라
**썸네일 재생성 시 원본 이미지를 메모리에 펼치던 것**이다.

> **정정(3-4)**: 여기서 "08-04 디스크 캐시가 그 경로를 끊었다"고 썼던 것은 과했다.
> 디스크 캐시는 같은 프로세스 안의 반복 생성만 막고, **재기동 후 첫 생성 비용은
> 그대로**다. 자세한 실측은 3-4에 있다.

이 시점에 MALLOC 환경변수는 대시보드에 반영되지 않은 상태였으므로, 이 개선은
그 설정의 효과가 아니다. MALLOC 값은 남은 잔여 누적에 대한 보험으로 유효하다.

회차 중 동시 접속 8건도 실패 0 · 평균 1.35초로 정상이었고, 완주 후 파이프라인은
원문 244 = 초안 244(미변환 0)로 깨끗했다.

## 3-3. 13시 회차 — 방해 없는 확정 측정

재배포가 끼지 않은 회차를 시작부터 완주까지 50초 간격으로 관측했다.

```
13:00:01  회차 시작   75.9MB
13:00:52              85.9MB   (+10.0)
13:01 ~ 13:10         85.9MB   (10분간 0.1MB도 안 움직임)
13:10:44  완주        85.9MB
```

**회차 증가 +10.0MB.** 전날 같은 구간이 **+155MB**였으므로 15배 개선이다.
주목할 점은 증가가 **처음 1분 안에 끝나고** 나머지 9분은 완전히 평평하다는 것이다.
기관을 돌수록 쌓이는 형태가 아니라 회차의 작업 메모리가 한 번 잡히는 형태다.

회차 도중 10개 화면 동시 요청을 3회(총 30건) 넣었고 **실패 0 · 중앙 1.2초**였다.
수집이 도는 중에도 열람이 멀쩡하다.

> **다만 +10MB가 매 회차 쌓이면** 하루 24회차에 +240MB다. 512MB 한도에서
> 이틀 정도에 도달한다 — 전날의 반나절보다는 크게 낫지만 0은 아니다. 남은
> 잔여분이 MALLOC 환경변수(4장)로 반납되는지는 **대시보드에 값을 넣은 뒤
> 하루치 곡선으로 확인해야 한다.** 이 리포트는 회차 1회분까지만 실측했다.

## 3-4. 정정 — 메모리 상승의 주범은 회차가 아니라 썸네일 생성이다

3-1·3-3에서 "썸네일 디스크 캐시가 그 경로를 끊었다"고 썼는데 **절반만 맞았다.**
15시 이후 추가 관측에서 더 정확한 그림이 나왔다.

**① 수집 회차 자체는 이제 공짜다.** 배포가 끼지 않은 연속 두 회차를 관측했다.

```
14:00:26 시작 186.5MB → 14:10:22 완주 186.5MB   (+0.0)
15:00:23 시작 183.4MB → 15:11:31 완주 183.4MB   (+0.0)
회차 사이 -3.1MB (오히려 줄었다)
```

**② 그런데 회차가 없는 시간에 크게 올랐다.**

```
13:13  77.4MB   (재기동 직후)
14:00  186.5MB  ← 회차 없이 +109MB
```

**③ 원인은 썸네일 생성이다.** `X-News-Express-Preview-Cache` 헤더로 확인했다.
캐시에 없던 썸네일 10건을 만들자 **183.4 → 193.2MB(+9.8MB, 1건당 약 1MB)**
올랐고 반납되지 않았다. 반대로 이미 캐시된 48건을 다시 요청하니 **+0.0MB**였다.

즉 디스크 캐시는 **같은 프로세스 안에서 반복 생성을 막을 뿐**이고, 재기동 후
처음 훑을 때의 생성 비용은 그대로다. 원문 244건을 새 프로세스에서 다 훑으면
산술적으로 **240MB 남짓** 오른다 — 전날 관측된 +155MB와 같은 자릿수다.

### ④ 디스크 캐시는 정상이다 — 앞선 의심은 기각

3-4를 처음 쓸 때 "디스크 캐시 경로가 임시라 재기동마다 사라지는 것 아니냐"고
의심했다. `backup_dir.parent / "previews"`가 `render.yaml`에만 있는
`NEWS_SUMMARY_BACKUP_DIR`에서 파생되기 때문이었다.

**15:45 재배포 직후 실측으로 기각됐다.** 메모리 캐시가 0.0MB인 새 프로세스에서
재기동 전에 만들어 둔 썸네일 20건을 요청하니 **20건 전부 `DISK`**로 돌아왔고
메모리는 **+0.0MB**였다.

```
프로세스 7a75ff9 · 80.5MB · 메모리캐시 0.0MB   (재기동 직후)
20건 요청 → {'DISK': 20} · 82.7 → 82.7MB
```

즉 **디스크 캐시는 영구 경로에 잘 살아 있고 재기동을 넘어 동작한다. 백업 파일도
사라지지 않는다.** 사용자에게 "백업 보관을 확인해 달라"고 했던 요청은 철회한다.

### 그러면 왜 오르나 — 남은 것은 신규 기사분

디스크에 없던 썸네일, 즉 **그 회차에 새로 들어온 기사**의 썸네일만 생성 비용을
치른다. 하루 244건 규모가 계속 갱신되므로 그만큼이 매일 쌓인다.

생성 코드는 이미 `Image.draft("RGB", ...)`로 JPEG를 축소 디코딩하고 있어
**펼치는 단계의 절약은 이미 최선**이다. 남는 1MB는 파이썬/glibc가 해제된
메모리를 OS에 돌려주지 않는 몫이므로, 남은 지렛대는 세 개다.

1. **메모리 반납 유도** — `MALLOC_ARENA_MAX` / `MALLOC_TRIM_THRESHOLD_`
   (2-1에서 `render.yaml`에 넣었으나 **대시보드 적용 여부는 여전히 미확인**)
2. 썸네일 생성을 서브프로세스로 분리 — 프로세스가 끝나면 OS가 확실히 회수한다
3. 플랜 상향

> **미확인으로 남는 것은 1번 하나뿐이다.** 대시보드 Environment에
> `MALLOC_ARENA_MAX`가 있는지만 확인하면 되고, 없으면 아래 두 줄을 넣으면 된다.
>
> ```
> MALLOC_ARENA_MAX       = 2
> MALLOC_TRIM_THRESHOLD_ = 65536
> ```

## 3-5. 최종 수치 — 하루 OOM의 산술이 맞아떨어진다

16시 회차 직후 독립 측정으로 1건당 비용이 재확인됐다.

```
10건 생성  183.4 → 193.2MB   (+9.8,  1건당 0.98MB)
20건 생성  148.8 → 168.5MB   (+19.7, 1건당 0.99MB)
```

결정적인 것은 **16시 회차로 들어온 새 기사 20건이 전부 `MISS`**였다는 점이다.
디스크 캐시는 재생성만 막을 뿐, **모든 기사는 생애 한 번 반드시 생성된다.**

```
하루 신규 기사 약 244건 × 1MB ≈ 244MB/일
Starter 한도 512MB
```

전날 관측된 곡선(75 → 230 → 293 → 331 → OOM)과 자릿수가 맞는다. **이것이 OOM의
전부이고, 수집 회차·DB·동시 접속은 무관하다.**

### "회차는 공짜"는 따뜻한 프로세스에 한한 말이다

3-4 ①에서 14시·15시 회차가 +0.0MB였다고 썼는데, 그 프로세스는 이미 183~186MB로
arena가 커져 있어 새 할당이 재사용된 상태였다. 15:50에 새로 뜬 프로세스는
80MB에서 16시 회차를 거치며 **148.8MB(+68MB)**가 됐다. 회차가 공짜인 게 아니라
**arena가 이미 크면 RSS가 더 안 오르는 것**이다.

### 권장 순서

1. **MALLOC 환경변수 확인·적용**(무료) — 대시보드에 있는지부터
2. 효과 없으면 **`malloc_trim(0)` 명시 호출** — 썸네일 생성 직후 `ctypes`로
   glibc에 반납을 강제한다. 임계값에 기대는 `MALLOC_TRIM_THRESHOLD_`보다
   확실하고, 리눅스가 아니면 무동작으로 두면 된다
3. 그래도 남으면 **생성을 서브프로세스로 분리**(프로세스 종료 시 OS가 회수)
4. 플랜 상향

## 3-6. 결착 (2026-08-06) — 20시간 무재기동 관측과 힙 반납

배포를 멈추고 20시간을 이어 관측해 밤낮으로 갈랐다. 이것이 결정적이었다.

```
밤(새 기사 없음)  20:46 183MB → 08:16 237.7MB 중 11시간이 ±1MB로 완전 평평
                  그 사이 수집 12회 완주 · 실패 0/24
낮(새 기사 유입)  08:47 237.7MB → 12:38 308.9MB  (+71.2MB, 재기동 0회)
```

**수집 회차·DB·접속량은 전부 무관하고, 상승원은 새 기사의 썸네일 생성 하나다.**
밤에 회차가 12번 도는 동안 1MB도 안 움직인 것이 그 증거다.

### 조치 — 생성 직후 `malloc_trim(0)` (`86e824f`)

원본을 펼쳤다 줄이는 메모리를 파이썬이 free해도 glibc가 arena에 쥔다.
생성 직후 명시적으로 반납을 강제했다. 캐시(메모리·디스크)에서 나온 건은 원본을
펼치지 않으므로 부르지 않는다. glibc가 아니면 무동작이고, 되돌리려면 호출
한 줄만 지우면 된다.

`MALLOC_TRIM_THRESHOLD_` 환경변수는 임계값에 기대는 방식이라 큰 일시 할당에
잘 듣지 않는다. 명시 호출이 확실하다.

### 효과 — 1건당 1.00MB → 0.19MB (81% 감소)

```
수정 전   10건 +9.8MB · 20건 +19.7MB      → 1건당 1.00MB
수정 직후 39건 +18.6MB                     → 1건당 0.48MB (일회성 비용 포함)
순수 측정 40건 +7.7MB (신규 회차분)        → 1건당 0.19MB
```

세 번째가 순수 값이다 — 연결·PIL 초기화 같은 일회성 비용을 이미 치른 뒤
새 회차가 물어온 신규 기사 40건으로 쟀다.

```
하루 244건 환산   244MB/일 → 47MB/일
한도 도달까지     약 1일   → 약 6일
```

### 서브프로세스 분리는 하지 않기로 한다

남은 0.19MB까지 없애려면 생성을 별도 프로세스로 돌려야 하지만, **하지 않는 것을
권한다.** 실제 재배포·재기동 주기가 6일보다 훨씬 짧아 도달 전에 리셋되고,
프로세스 분리는 fork·스레드 상호작용 위험과 지연을 새로 들인다. 남은 상승이
관측으로 문제를 일으킬 때 다시 꺼내면 된다.

## 3-2. 추가 검증 (로그·세션·스케줄러)

- **로그 회전**: 상한 20,000B × backup 3 조건에서 파일 4개·79KB로 정확히 제한됨. 운영값 2MB × 6 = 최대 12MB로 디스크가 로그로 찰 위험 없음.
- **세션 보안**: CSRF 토큰 없는 로그인 400 거부 · 운영 관리 31분 경과 시 자동 잠금 302 · 로그아웃 후 운영 차단하면서 대시보드는 공개 유지.
- **스케줄러 안전장치**: 죽은 스레드 자체 복구 동작 · 복구 실패 시 예외 격리 · 먹통 판정은 35분 지연에서만 발동하고 **실행 중인 회차는 60분이 지나도 죽이지 않음**.
