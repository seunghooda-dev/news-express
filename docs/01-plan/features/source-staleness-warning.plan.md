# 기관 정체 감지 경고 계획 (2026-11-23)

## 배경

구례군 보도자료 게시판이 2026-10-22 이후 4주째 새 글이 없다는 것을 우연히 알았다(11/19). 로컬 중계는 정상으로 돌고 있었고
(매시 종료 코드 0), 서버 상태도 "중계 정상"이었다. 기관이 조용히 멈춰도 알 방법이 없다 — 상세 헬스체크의 수집 점검은
"수집이 실패했는가"만 보고, 중계 감시(`relay-heartbeat`)는 "프로세스가 돌았는가"만 본다.

기존 근접 기능과의 관계는 아래와 같다.

| 기존 | 보는 것 | 못 보는 것 |
|---|---|---|
| `source_collection` | 수집 요청의 성공·실패 | 성공했지만 글이 며칠째 그대로인 기관 |
| `relay` | 중계 프로세스의 생존 | 중계는 살아 있는데 기관이 멈춘 경우 |
| 수집 이상치(`_collection_anomaly_snapshot`) | DB에 **저장된** 글의 오늘 0건·급감·급증 | 3영업일 보관 밖의 긴 정체 |

`relay-heartbeat.plan.md`는 "기관별 원문 0건 경보"를 비목표로 뒀다 — 구례처럼 군청이 안 올려서 0건인 사례가
오경보라는 이유였다. 이번에는 **원문 0건이 아니라 목록의 최신 게시일의 나이**를 영업일로 본다. 구례는 오경보가 아니라
이 기능이 처음 잡는 진짜 정체다.

## 결정

### 무엇을 기록하나
수집 때마다 기관 목록(보관 필터 이전)에서 가장 최근 게시일을 기관별로 `app_metadata`에 남긴다.

- 키 `source_latest_published:<source_id>`, 값 JSON `{"latest": "YYYY-MM-DD", "checked_at": <UTC ISO>}`.
- 기관별 키다. 하나의 JSON 맵으로 합치면 서버(:08)와 중계(:00)가 읽고-고치고-쓰다 서로 덮어쓴다. 서버는 중계 기관을 수집하지
  않으므로(`collection_excluded_source_ids`) 기관별 키의 작성자는 항상 하나다.
- 원문 자체는 3영업일만 보관하므로(`prune_press_releases_outside_retention`) DB의 `press_releases`로는 그보다 긴 정체를 볼 수 없다.
  그래서 별도 기록이 필요하다.
- 호출 지점은 `collect_source_with_fallback`이 돌려준 직후·보관 필터 직전이다. 서버 정기 수집(`collect_enabled_sources`)과 로컬 중계가
  모두 이 지점을 지난다. 일시 장애 재검증·자동 복구 경로에는 넣지 않는다 — 다음 정기 회차가 기록한다.
- 헬퍼는 `service.record_source_latest_published(store, source, releases)`. 기록이 실패해도 경고 로그만 남기고 수집의
  성공·실패 판정에 영향을 주지 않는다. 파싱되는 날짜가 하나도 없으면(빈 목록, "미정" 등) 쓰지 않아 직전 값을 보존한다.
  내일 이후의 날짜(오타)는 무시한다 — 최댓값이 미래로 튀면 영영 정체가 안 잡힌다.
- 날짜 해석은 기존 `press_release_published_date`를 재사용한다(보관 필터와 같은 규칙).

### 어떻게 판정하나
`web._source_staleness_health_payload(store, config_path, now=None)`가 설정의 기관을 돌며 기록이 있는 곳을 점검한다.

- 정체 = 최신 게시일부터 **어제까지의 영업일 수 ≥ 5**(`business_days_between`, 공휴일 반영). 일주일 내내 새 글이 없는 기관이다.
  달력 일수가 아니라 영업일이라 주말·연휴가 오경보를 만들지 않는다.
- **오늘은 세지 않는다**(독립 검토에서 지적, 반영). 오늘을 센 첫 구현은 "4영업일 무게시 + 오늘 아직 안 올림"을 자정부터
  정체로 봐서, 매주 같은 요일에 올리는 기관(로그상 강진은 화요일마다)이 그 요일 새벽에 오경보를 냈을 것이다. 어제까지 5영업일을
  꽉 채워 못 올린 기관만 잡는다. 응답의 `business_days`도 오늘 제외 값이다.
- 마지막 확인(`checked_at`)이 48시간보다 오래된 기관은 건너뛴다 — 그때는 수집·중계 자체가 멎은 것이라 `source_collection`·`relay`
  경고의 몫이다. 서버가 수집하지 않는(`enabled: false`) 중계 기관도 기록이 있으면 점검한다.
- 기록이 하나도 없으면(배포 직후 첫 회차 전) `neutral`이다.
- 상태는 `ok`/`warning`/`neutral`. 경고는 `warning`까지만 올린다(수집 실패가 아니므로 error로 올리지 않는다).
- 점검 함수는 내부에서 예외를 처리한다 — `/healthz/details`에는 바깥 보호가 없어 예외가 500이 된다.
- 응답 키: `source_staleness_status`, `_message`, `_count`, `_sources`(기관·최신 게시일·영업일 수), `_threshold_business_days`.

### 어디에 연결하나
- `/healthz/details`(`_healthz_response`)와 운영 화면 서비스 상태(`_operations_service_status_report`) **양쪽** — 두 경로는
  자동으로 동기화되지 않는다.
- `_service_health_summary`에 component `source_staleness` 추가(warning/error일 때만 이슈).
- `OPERATIONS_COMPONENT_CARD_MAP`에 기존 카드 `ops-collection-coverage`로 매핑한다(`relay`와 같은 카드). 새 카드는 만들지 않는다.
- 로컬 중계(저장소 밖)의 `_relay_one`에서 보관 필터 앞에 호출한다. 다른 PC의 저장소가 낡아 헬퍼가 없어도 중계가 죽지 않도록
  임포트는 `ImportError`를 허용한다.
- 값 읽기는 `Store.get_app_metadata_prefix(prefix)` 한 번의 쿼리로 한다(기관 수만큼 쿼리를 돌리지 않는다).

## 하지 않는 것
- 기관별 임계값 설정(`stale_after_days`) — 이번엔 전역 5영업일 하나다. 드물게 올리는 기관이 오경보를 만들면 그때
  `Source`에 기본값 있는 필드로 추가한다.
- 경고를 끄는 설정 — 구례는 지금 정체가 사실이므로 경고가 뜨는 것이 맞다. 군이 다시 올리면 저절로 사라진다.
- 목록 행 전체의 날짜 — 수집이 돌려주는 것은 검증을 통과한 글(본문 80자 이상 등)이라 가장 새 글이 사진뿐이거나 본문이 짧으면
  최신 게시일이 과소평가될 수 있다. 5영업일 문턱이 이 오차를 흡수하며, 정확히 하려면 수집기 안에 훅이 필요해 이번 범위를 넘는다.
- 일시 장애 재검증·자동 복구 경로의 기록, 신규 운영 화면 카드.

## 검증
- 시험 먼저: 저장소 메타데이터 접두어 조회, 헬퍼(최댓값·미래 날짜 무시·파싱 불가 무기록·저장 실패 무영향), 판정(정체·정상·
  경계 5영업일·주말·오래된 확인·설정에 없는 기관·비활성 중계 기관·기록 없음), 요약 이슈, `/healthz/details` 키, 운영 화면 요약.
- 중계 시험(저장소 밖): 호출됨, 헬퍼가 없거나(None) 실패해도 기관 처리가 계속됨.
- 배포 뒤 첫 회차가 기록을 채우면 `/healthz/details`에서 구례가 정체로 나오는지 확인한다(예상: 22영업일 안팎).

## 되돌리는 법
점검 함수 호출 두 줄과 `_service_health_summary` 항목을 빼면 경고가 사라진다. 기록 키는 `app_metadata`에 남지만 무해하다.
