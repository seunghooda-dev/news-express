## 1. 왜 필요한가 — 실측

2026-11-18 점검에서 강진·광주 남구·구례 원문이 서비스에 0건이었다. 로컬 중계가
사무실 새 PC로 옮겨졌다가(9/17) 멈춘 것으로 보이는데, **언제부터 멈췄는지 알 방법이 없었다.**
중계 재가동 즉시 강진 12건·남구 3건이 신규 저장돼 누락이 실증됐다. 서버 상태는
내내 "정상 범위"로 보였다 — 서버가 해당 기관을 `enabled: false`로 두고 있어서
기존 수집 점검(오늘 수집 커버리지 등)이 이 기관들을 아예 세지 않기 때문이다.

## 2. 목표와 비목표

**목표**
- 중계가 마지막으로 돈 시각을 DB에 남기고, 서버가 그 나이를 점검한다.
- 3시간(= 매시 정각 3회) 넘게 기록이 없으면 서비스 상태에 경고를 올린다.

**비목표 (이번엔 안 한다)**
- 기관별 "원문 0건" 경보 — 구례처럼 군청이 안 올려서 0건인 정상 사례가 있어 오경보가 난다.
- 외부 알림 발송(메일·메신저). 이번 변경은 운영 화면·헬스 JSON 노출까지다.
- 기관별 성공·실패 이력 저장. 강진은 매일 06시 사이트 점검으로 한 회차씩 실패하는 정상 패턴이 있다.

## 3. 설계 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 기록 방식 | `app_metadata` 키 `relay_heartbeat`에 JSON `{"updated_at": UTC ISO, "host": PC 이름}` | 기존 스냅샷(`_metadata_json_report`·`_age_minutes`)을 그대로 재사용. 새 테이블·API 없음 |
| 기록 주체 | 중계 스크립트 `gangjin_relay.py`가 매 실행 끝에 1회 | 저장소 밖 파일이라 이 저장소 코드는 읽기만 한다 |
| 기록 시점 | 일부 기관이 실패해도 DB에 닿았으면 기록 | "중계 프로세스가 돌았는가"를 보는 지표다. 기관별 성공 여부는 로그에 있다 |
| 경고 조건 | 필수 기관 중 비활성(= 중계 대상)이 있고, 기록이 없거나 180분 초과 | 모든 기관이 서버 수집으로 돌아오면 경고가 저절로 사라진다 |
| 심각도 | warning 한 단계 | 중계 중단은 일부 기관 누락이지 서비스 중단이 아니다 |
| `host` | 저장하고 메시지에 노출 | 두 PC가 동시에 도는 구성에서 어느 쪽 기록인지 구분한다 |

## 5. 배포 순서

1. 중계 스크립트를 먼저 고친다(기록만 쌓이고 서버는 아직 안 읽는다 — 무해).
2. 서버 코드를 `scripts/safe_deploy.py`로 배포한다. 배포 직후 다음 정각 회차 전까지 "기록 없음" 경고가 뜰 수 있다 — 1번을 먼저 했으면 이미 기록이 있어 뜨지 않는다.
3. 새 PC가 아직 살아 있어 옛 스크립트로 돌면 기록을 못 남기지만, 이 PC 기록이 있으면 경고가 나지 않는다(가장 최근 기록만 본다).

## 6. 검증

- 단위 테스트 4경우 + 전체 게이트 통과.
- 배포 후 `/healthz/details`에 `relay_status: ok`와 `relay_host`가 보이는지 실측.
- 중계 작업을 잠시 끄고 3시간 지나 경고가 뜨는지는 시간이 오래 걸려 **하지 않는다**. 대신 테스트가 시각을 주입해 같은 경로를 검증한다.

## 7. 한계

- 알림이 아니라 **표시**다. 누군가 운영 화면이나 `/healthz/details`를 봐야 보인다. 메일·메신저 알림은 별도 결정 사항이다.
- 중계 스크립트가 DB에 닿지 못하면 기록도 못 남긴다. 그 경우가 바로 경고가 뜨는 경우이므로 의도대로다.
