# 중계 견고성 · 서버 경고 정리 계획 (2026-11-19)

2026-11-19 개선 백로그(서브에이전트 4건 조사)의 1·2번 묶음이다. 근거와 조사 상세는 메모리
`news-express-improvement-backlog-1119`에 있다. 3~6번(첨부 미리보기, 중계 상태 가시성, 차단 전조, 중계 PC 설정)은
이번 범위가 아니다.

## A. 중계 견고성 (저장소 밖 `news-express-gangjin-relay\gangjin_relay.py`)

### 문제
- 예약 실행(`pythonw`)에는 stderr가 없어서, 처리 안 된 예외로 죽으면 로그에 흔적이 남지 않는다.
  2026-11-18 11:08 Supabase 풀러 연결 리셋(`psycopg.OperationalError`)이 그랬다.
- try 밖 지점 — `add_press_release`, `repair_missing_published_dates`, `load_sources`, `set_app_metadata`, 임포트.
  DB 오류 한 번이 그 회차의 나머지 기관과 heartbeat를 죽인다.

### 결정
| 항목 | 내용 |
|---|---|
| 로깅 | 임포트 전에 설정한다. 로그 파일 경로는 `RELAY_LOG_PATH`로 바꿀 수 있다(시험이 실제 로그를 더럽히지 않도록). 저장소 임포트 실패도 로그에 남긴다 |
| 최상위 보호 | `main()`이 예상 못한 예외를 `logger.exception`으로 남기고 종료 코드 1을 돌려준다. 시작·종료 줄(종료 코드, 걸린 시간)을 항상 남긴다 |
| 기관 단위 | `_relay_one` 전체를 try로 감싼다. 한 기관의 오류가 다음 기관을 막지 않는다. 글 단위 저장 실패도 개별로 잡아 나머지 글을 계속 저장한다(실패가 있으면 그 기관은 실패로 센다). 설정에 없는 기관 id는 실패로 세고 나머지는 돈다 |
| DB 재시도 | `psycopg.OperationalError`(연결 오류)만 3초 뒤 한 번 더 시도한다. 대상은 DB 쓰기 한 번짜리 — `add_press_release`(URL로 중복을 막아 안전)와 heartbeat(같은 값 upsert). 재시도 후에도 연결이 안 되면 그 기관의 남은 글은 건너뛰고(연결 시도로 시간을 쓰지 않는다) 다음 기관으로 간다. 데이터 오류(NUL 문자 등)는 재시도하지 않고 그 글만 건너뛴다 |
| 게시일 보정 | 부가 작업이라 재시도하지 않고(사이트를 다시 두드리고 시간을 두 배로 쓴다) 실패해도 그 기관을 실패로 세지 않는다 — 경고와 트레이스만 남기고 이미 저장한 글의 요약 줄을 유지한다. DB 연결이 끊겨 저장을 중단한 기관은 보정도 건너뛴다 |
| heartbeat | `finally`에서 기록한다. 기관 처리 중 예외가 나도 "프로세스가 살아 있다"는 기록은 남는다. heartbeat 기록 자체가 실패하면 로그에 남기고 종료 코드 1 |
| 종료 줄 | `main()`이 `SystemExit`(DATABASE_URL 오류 등)도 잡아 종료 줄을 남긴다 |
| 마감 | 작업 제한(15분)에 걸려 heartbeat 없이 죽지 않도록, 회차가 420초를 넘으면 아직 시작하지 않은 기관은 건너뛰고(실패로 센다) heartbeat를 쓴다. 수집 중인 기관을 끊지는 않으므로, 시작 뒤 최악 수 분(보정 20건×HTTP 20초 등)을 감안해 600초가 아니라 420초로 둔다. 실측 최장 회차 390초라 평소엔 걸리지 않는다 |

검토자(읽기 전용 서브에이전트 2명)가 지적해 반영한 것 — 마감이 실제 상한이 못 됨, `SystemExit`가 종료 줄을 우회함,
설정에 없는 기관 id가 회차 전체를 죽임, 보정을 재시도하면 HTTP까지 되풀이됨, 재시도 경고에 원인 문구가 없음.
반영하지 않은 것 — 응답 없는 연결을 끊는 워치독(Store에 읽기 timeout이 없음)은 이번 범위 밖이다.

### 시험
저장소 밖이라 저장소 게이트에 들어가지 않는다. 중계 폴더의 `test_gangjin_relay.py`를 저장소 venv로 돌린다.
가짜 Store·가짜 수집 함수로 — 기관 하나의 예외가 다음 기관을 막지 않음, DB 1회 실패 후 재시도 성공,
글 하나의 저장 실패가 나머지 글을 막지 않음, 예외가 나도 heartbeat 기록, 최상위 예외가 종료 코드 1과
스택 트레이스 로그를 남김, 마감 초과 시 남은 기관 건너뜀.

## B. 서버 경고 정리 (저장소)

### 문제 1 — "Gemini 큐 점검 N분 전" 오탐
큐 점검 스냅샷(`auto_queue_drain_status_snapshot`)은 대기 건이 있을 때만 쓴다(`scheduler.py` 조기 반환).
대기열이 비면 몇 시간째 안 갱신되는 것이 정상인데 신선도 점검(`_operations_snapshot_freshness_payload`)이
180분을 넘기면 경고한다. 11/19 06:15 실측: 692분 전.

**결정**: 대기 건이 없을 때는 큐 점검 스냅샷의 나이를 경고로 세지 않는다. 대기 건이 있는데 갱신이 멈춘 것은
진짜 문제라 그대로 경고한다. 점검 목록(`checks`)에는 나이를 계속 싣는다. 대기 건 확인은 5쿼리짜리
`pending_press_release_summary` 대신 `Store.has_pending_press_release()`(`LIMIT 1` 존재 확인)를 쓰고, 조회가
실패하면 대기 건이 있는 것으로 본다(지연을 숨기지 않고, 헬스체크가 500이 되지 않는다). 알려진 한계 — 야간
휴지 뒤 첫 수집으로 대기 건이 생기면 다음 유지보수 틱(최대 약 15분)까지 일시 경고가 뜰 수 있고 저절로 풀린다.

### 문제 2 — "일시 장애 재검증 4곳" 잔류
`_source_collection_health_payload`의 `latest_rows`가 비활성 기관을 거르지 않아, 서버가 마지막에 시도한 실패
행이 영구히 남는다(영광+강진·남구·구례). 중계 기관이 늘 때마다 하나씩 늘어난다.
운영 화면용 `_operations_health_report`는 2026-08-04에 이미 같은 처리를 했다(`disabled_source_ids`).

**결정**: 같은 방식으로 비활성 기관을 `recent_rows`·`latest_rows`에서 뺀다. 설정을 못 읽으면 종전대로
거르지 않는다(보수적). 비활성 기관의 실패는 서버 수집 실패가 아니고, 중계 생존은 heartbeat가 따로 본다.
설정에 없는 기관(시험용 `sample-source` 등)은 그대로 남는다.

### 하지 않는 것
- production_readiness 필수 2건(접근 보호 강제 비활성·상세 헬스체크 공개)과 권장 2건 — 8/18 공개 운영 결정의
  결과이고 "의도된 공개 운영" 플래그는 Render 환경변수가 필요한 사용자 결정이다. 이번에 건드리지 않는다.
- 비활성 기관 수집 실패를 어디에도 안 보이게 하는 것은 아니다 — 중계 기관별 실패 가시성은 백로그 4번이다.
