## 1. 무엇을 만들었나

매일 만들어지는 기사 초안과 첨부 사진을 카드뉴스로 묶어 주민에게 전하는 경로.

```
수집·초안(기존)  →  ①후보 추천 8건  →  ②사람이 3~5건 확정
                 →  ③문안 생성(Gemini)  →  ④카드 합성  →  ⑤/card-news 공개
```

**기존 수집·초안 파이프라인은 건드리지 않았다.** ①③은 읽기만 하고 ④는 결과를
따로 쌓는다.

| 파일 | 역할 |
|---|---|
| `cardnews.py` | 1080×1350 카드 합성 (웹·DB 무의존 순수 모듈) |
| `cardcopy.py` | 초안 → 카드 문안, 규격 검증 |
| `cardnews_service.py` | 통합 계층 — **사진 출처 보장 책임** |
| `card_picks.py` | 후보 점수·편중 차단 |
| `memory.py` | 힙 반납 (썸네일 경로와 공유) |
| `scripts/safe_deploy.py` | 회차 중 배포 거절 |

테스트 **65건** 신규, 전체 게이트 **444 통과**.

## 2. 실측으로 정한 것들

계획을 쓰기 전에 재료를 쟀고, 그 수치가 설계를 바꿨다.

| 실측 | 설계에 미친 영향 |
|---|---|
| 이미지 보유율 50/50건(100%) | 사진 없는 예외를 주요 경로로 안 짬 |
| 원본 5건 중 3건만 1080px 이상 | **저해상도 40%는 확대 금지, 텍스트 카드로 전환** |
| 표본 8장 전부 가로형(1.33~1.92) | 4:5 상하 분할 채택, 좌우 크롭 금지 |
| 초안 215~525자 | 카드 3~5장이 자연스러움 |
| Pillow가 woff2 직접 읽음 | **글꼴 파일 추가 불필요** |
| 세트당 26.3초 | Plan 성공기준 "1분 이내" 충족 |

## 3. 구현 중 잡은 결함 넷

전부 **문서가 아니라 실행**에서 드러났다.

### 3-1. 화재 사진에 예식장 문구 (가장 위험)

확인 스크립트가 대시보드에서 사진을 긁어와, **화재 조사 현장 사진에 "공공예식장
개방" 안내문**이 붙은 카드가 나왔다. 방송사가 내보내면 버그가 아니라 신뢰 사고다.

주의로 막지 않고 구조로 막았다 — 생성 진입점이 `draft_id`만 받고, 사진은 그
초안이 속한 원문의 첨부에서만 가져온다. 다른 기사 첨부를 요청하지 않는 것을
회귀 테스트로 고정했다.

### 3-2. 좌우가 잘리고 있었다

설계에 "크롭이 아니라 상하 분할이라 인물·현장이 잘리지 않는다"고 써 놓고,
구현은 밴드를 꽉 채운 뒤 중앙 크롭이었다. 밴드 비율 1.379보다 넓은 사진은
좌우가 날아갔는데 표본이 1.33~1.92다. **설계가 사실과 달랐다.**

폭을 먼저 맞추도록 바꾸고, 좌우 끝에 표식을 둔 사진으로 잘림을 픽셀로 잡는
테스트를 만들었다.

### 3-3. 폭염 기사 일곱 번

기관 편중은 막았는데 추천 8건 중 7건이 폭염 기사였다. 기관은 일곱 곳으로
달랐지만 주민이 보기엔 같은 소식이다. 주제 상한을 넣어 2건으로 줄였다.

### 3-4. 문안을 고칠 수 없었다

Plan 성공기준인데 AI 재생성밖에 없었다. 편집 폼을 붙였고, 저장된 문안으로
이미지만 다시 그린다 — AI를 부르면 고친 글자가 덮인다.

## 4. 갭 분석

| 항목 | 판단 |

## 6. 사용자가 할 일

1. 공개 화면 `/card-news` 오른쪽 위 **"카드 만들기"**(로그인 상태에서만 보인다)
2. 추천 후보 중 **3~5건을 골라 카드 만들기**
3. 문안을 확인하고 필요하면 고친다
4. **발행하기** — 이때부터 주민에게 보인다
5. `/card-news` 링크를 카톡·밴드에 공유(카드가 미리보기로 뜬다)

## 7. 후속 (2026-08-10) — 한 장으로

발행 경로를 실제로 돌려 보고 사용자가 세 가지를 지적했다. **전부 문서가 아니라
사용에서 나왔다.**

| 지적 | 처리 | 커밋 |
|---|---|---|
| 카드에 사진이 하나도 없다 | 문턱 1080 → **800**. 실측에서 사진 있는 초안의 43%가 글자만 남고 있었다 | `322cf98` |
| "사진 한 장에 기사를 전부 축약해서 넣어" | **기사 한 건 = 카드 한 장** | `cd13883` |
| "카드만들기가 안보여" | 공개 화면 → 관리 화면 링크 | `9220e66` |
| "문체가 너무 딱딱한데" | 소제목 명사 종결 규칙을 뒤집고 `~합니다`체로. 사실 보존 규칙은 유지 | `2317ca5` |
| "내가 만든 건 4장에 한 기사가 있는데" | **다시 그리기** — 저장된 문안으로 이미지만 재합성 | `2317ca5` |

측정으로 정한 것 둘.

- **본문 상한 70자** — 55자는 추정치였고 57자 문안 하나에 세트가 통째로 거절됐다.
  요점 2~3개면 120자, 4개면 100자가 실제 한계다. 상한은 거절선, 길이 취향은 프롬프트
  목표치(30~45자)가 잡는다.
- **해상도를 보는 후보 점수는 안 만든다** — 가점 있음/없음으로 상위 8건을 비교하니
  8/07은 순서까지 같고 8/10은 한 자리만 밀렸다. 초안의 92~95%가 첨부를 가져 +2가
  상수다. 설계 §10에 근거를 남겼다.

### 되살린 죽은 코드 하나

`card_picks._score()`의 "첨부 있음 +2"가 **운영에서 한 번도 켜진 적이 없었다.**
순위 SQL이 첨부 수를 세는 서브쿼리를 빠뜨리고 있었다. §5에 "가점이 해상도를 안
본다"고 한계를 적어 뒀는데, 실은 가점 자체가 안 걸리고 있었다.

### 독립 검토가 잡은 것 (교훈)

한 장 전환 뒤 `code-analyzer`를 붙여 심각 결함 2개를 잡았고 **둘 다 그날 내가 넣은
것**이다. 자체 검토 + 게이트 469건 통과 + 시안 육안 확인을 다 하고도 못 봤다.

1. 요점을 덜어낼 때 소제목과 본문이 별개 블록이라 **본문만 먼저 지워졌다** —
   "접수는 이렇게 하시면 됩니다"만 남고 접수처가 사라진 카드가 발행 상태로 나가는
   경로. 하필 그날 새로 만든 "다시 그리기"에서만 터졌다.
2. 카드가 한 장이 됐는데 사진은 4장을 그대로 받아왔다 — 요청당 최대 165MB.
   threads 8 · 512MB · OOM 재시작 이력이 있는 서비스다.

공통점은 **바꾼 쪽이 아니라 짝이 안 맞게 된 쪽**이 터졌다는 것이다. 검토 결과를
그대로 믿지 않고 재현 스크립트로 확인한 뒤 고쳤고, 틀렸다고 본 지적
(`lru_cache` 스레드 안전성, `close()` 누락)은 근거를 확인하고 그대로 뒀다.

게이트 **469 통과**, 6커밋 전부 배포 후 라이브 확인(`commit c6dcdb5 | mem 79.3MB`).
