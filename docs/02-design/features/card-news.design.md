# 카드뉴스 발행 (card-news) — Design

- **작성일**: 2026-08-09
- **선행 문서**: [Plan](../../01-plan/features/card-news.plan.md)
- **개정**: 2026-08-10 — **기사 한 건 = 카드 한 장**으로 전환(§10)
- **전제**: 전달은 자체 웹, 하루 3~5건 엄선, 4:5 상하 분할 레이아웃

## 1. 전체 흐름

```
수집·초안 (기존)
     │
     ▼
① 후보 추천      하루치 초안 중 8건을 점수 규칙으로 고른다  (읽기 전용)
     │
     ▼
② 관리자 확정    사람이 3~5건을 고른다                   (기존 검수 화면 옆에)
     │
     ▼
③ 문안 생성      초안 → 제목 + 요점 2~4개                (Gemini, 읽기 전용)
     │
     ▼
④ 카드 합성      1080×1350 PNG **한 장**                 (Pillow, 디스크 저장)
     │
     ▼
⑤ 공개           /card-news 에서 주민이 본다              (로그인 불필요)
```

**기존 파이프라인을 건드리지 않는다.** ①③은 초안을 읽기만 하고, ④는 결과를
디스크에 따로 쌓는다. 수집·초안 생성 경로에 손대지 않으므로 회귀 위험이 낮다.

## 2. 카드 사양

| 항목 | 값 | 근거 |
|---|---|---|
| 크기 | **1080 × 1350** (4:5) | 모바일 세로 화면을 가장 크게 쓴다. 인스타로 확장할 때도 그대로 쓸 수 있다 |
| 장수 | **기사 한 건 = 카드 한 장** | 넘길 다음 장이 없어야 신청 기한·대상이 함께 읽힌다(§10) |
| 구성 | 위에서부터 사진 → 제목 → 요점 전부 → 구분선 → 출처·날짜 | 한 장에 기사가 다 들어간다 |
| 사진 밴드 | 카드 높이의 **34~52%**, 글 분량에 따라 가변 | 요점이 짧은 기사는 사진을 키워 아래 빈자리를 없앤다 |
| 글자 크기 | 6단 사다리 `(58,38,32)` → `(34,26,22)` | 요점 2개인 기사와 4개인 기사가 같은 높이를 나눠 쓴다. 큰 것부터 넣어 보고 안 들어가면 한 단 줄인다 |
| 넘칠 때 | 사다리를 다 써도 안 들어가면 **마지막 요점부터 통째로 덜어낸다** | 소제목만 남고 본문이 사라지면 "접수는 이렇게" 뒤가 빈 카드가 나간다 |
| 바탕색 | **검정(`#111111`)** | 흰 배경이 끼면 산만하다(2026-08-09 사용자 지시) |
| 사진 배치 | **폭에 맞추고 좌우는 절대 안 자른다.** 높으면 위아래만 자르고, 낮으면 위아래를 배경으로 채운다 | 초기 구현이 밴드를 꽉 채우느라 넓은 사진의 좌우를 잘랐다(2026-08-09 갭 분석에서 적발·시정) |
| 글꼴 | `PretendardVariable.woff2` (기존 자산) | Pillow가 직접 읽는 것을 확인 |

### 사진을 쓸지 말지

```
폭 >= 800px  그리고  폭 <= 높이 × 3   →  사진 레이아웃
그 밖                                 →  텍스트 중심 레이아웃
```

판정 축은 **긴 변이 아니라 폭**이다. 밴드에 넣을 때 폭으로 배율을 잡으므로 긴 변으로
재면 700×2000 같은 세로 사진이 확대돼 버린다(2026-08-09 검토에서 적발).

문턱은 처음에 카드 폭 그대로인 1080이었다. 확대를 0으로 막는 값이지만,
**2026-08-07 금요일 전량 실측에서 사진이 붙은 초안의 43%가 글자만 남았다**(110건 중
47건, 점수 상위 3건이 전부 여기 걸림). 지자체 CMS가 1000·980·780px로 줄여 내보내는
탓이고 가장 흔한 폭이 1000px이다. **사진이 아예 없는 카드가 손해가 더 크다**고 보고
1.35배까지 확대를 허용해 800으로 내렸다 — 110건 중 90건(82%)에 사진이 실린다.

가로로 지나치게 납작한 것(폭 > 높이 × 3)은 사진이 아니라 배너다. 밴드에 넣어 봐야
위아래가 검정으로 남으므로 안 쓴다.

## 3. 문안 생성 (③)

기존 `analyzeSubtitles` 계열과 같은 **읽기 전용 분석 액션**으로 붙인다.
초안 문서를 변형하지 않으므로 되돌리기·자동저장 대상이 아니다.

```
입력   초안 제목 + 본문(215~525자) + 기관명
출력   {
         cover: "6~36자",
         cards: [{ heading: "4~16자", body: "20~70자" }, ...요점 2~4개],
         tags: [...최대 5]
       }
```

**요점마다 소제목과 본문을 함께 담는다.** 처음에는 문장 하나만 넣었는데 카드가
휑하고 무슨 얘긴지 한눈에 안 들어왔다(2026-08-09 사용자 지적 "내용이 조금 빈약해").

**상한은 한 장 전환(§10)에서 크게 줄었다.** 제목과 요점 전부가 사진 아래 660px
남짓을 나눠 쓰므로, 본문 110자를 그대로 두면 요점 네 개가 카드 높이를 두 배로
넘긴다. 다만 상한은 **배치가 실제로 못 견디는 선**이어야 한다 — 실측(2026-08-10)에서
요점이 2~3개면 120자도 안 잘리고 4개일 때 100자가 한계였는데, 55자로 좁혀 뒀더니
57자 문안 하나 때문에 세트가 통째로 안 나왔다. 상한은 70으로 두고, 길이 취향은
프롬프트의 **목표치(30~45자)** 가 잡는다. 규격을 좁게 잡으면 멀쩡한 문안이 계속
거절된다는 2026-08-09의 교훈이 여기서 반복됐다.

옛 형태(문자열 리스트)로 저장된 세트도 그대로 읽힌다 — 소제목 없이 본문만 렌더한다.

**검증은 컨트롤러에서 한다** — 반환값을 믿지 않고 장수·글자수를 다시 확인하고,
초과하면 자르지 말고 **거절한다**. 규격 미달은 모델을 바꾸면 통과하는 일이 잦아
다음 모델로 넘어가고(Flash → Flash-Lite), 끝내 못 맞추면 시도한 모델을 모두 적어
실패시킨다. 잘린 문장이
카드에 박히면 사람이 고치기 더 번거롭다.

### 문안 품질 실측 (2026-08-09)

프롬프트를 두 번 고치며 실제 기사 10건씩으로 쟀다. **범위만 주면 모델이 상한을
목표로 삼는다** — 표지 9건 중 2건이 정확히 상한이었고, 좋은 카피가 1자 초과로
거절되고 제목 재배열본이 채택된 사례까지 나왔다. "목표치 + 절대 상한"으로 다시
쓰고 표지 상한을 30 → 36으로 넓혔다.

| 지표 | 1차 | 2차(개선 후) |
|---|---|---|
| 소제목 명사 종결 | 24/26 (92%) | **14/30 (47%)** |
| 주체(인물·기관) 명시 | 0/5 | **10/10** |
| 어림 표현 절삭("600여 곳"→"600곳") | 발생 | **0건** |
| 없는 명칭 생성("현장지원단"→"농업지원단") | 1건 | **0건** |
| 날짜 월 보간("오는 28일"→"8월 28일") | 2/12 | **0건** |
| 본문 100자 이상 | 6/26 | 3/30 |

2차에서 **새 날조 두 건**이 드러나 3차로 막았다.

- 접수 방식 날조 — 원문 "20명을 대상으로"가 "**선착순** 20명"이 됐다. 주민이
  행동을 바꾸는 정보라 숫자 오류보다 해롭다.
- 확정도 승격 — 원문 "의견을 교환·공감"이 표지에서 "협력이 **시작됩니다**"가 됐다.

프롬프트 예시에 쓴 낱말이 사실 표현으로 새어 나오는 것도 확인했다("교육비"가
예시 어휘인 "수강료"로 바뀜) — 예시는 형태만 참고하라고 명시했다.

**운영 주의** — `gemini-3.5-flash`는 무료 티어 일일 20회 한도가 있다. 소진되면
예비 모델로 넘어간다. 쿼터 오류에는 **재시도하지 않는다** — 한도만 더 빨리 깎는다.

## 4. 후보 추천 (①)

하루 244건을 사람이 다 보게 할 수 없다. 8건으로 줄이고 사람이 3~5건을 고른다.

추천 기준 — **주민 생활에 직접 영향** > 마감·신청 기한 있음 > 구체 수치 있음 >
첨부 있음. 인사·간담회·표창 같은 행정 소식은 감점한다.

**LLM이 아니라 키워드 점수 규칙**이다(`card_picks.py`). 비용이 0이고 결과가
재현되며, 사람이 왜 올라왔는지 볼 수 있어 이 단계에는 이쪽이 낫다.

편중은 두 축으로 막는다.

- **기관당 최대 2건** — 한 기관 홍보물처럼 보이면 주민이 안 본다.
- **주제당 최대 2건** — 실측에서 폭염 주간에 8건 중 7건이 폭염 기사로 채워졌다.
  기관은 일곱 곳으로 달랐지만 주민이 보기엔 같은 소식 일곱 번이다.
- 주제가 쏠려 명단이 짧아지면 **최소 5건까지만** 상한을 푼다. 비슷한 기사로
  8칸을 억지로 메우면 고르는 데 방해만 된다.

주의 — "첨부 있음" 가점은 **첨부 존재 여부만** 본다. 원본 해상도까지 보려면
내려받아야 해서, 1080px 미만이라 실제로는 텍스트 카드가 될 기사도 가점을 받는다.

추천은 **제안일 뿐 자동 발행하지 않는다.** 최종 선택은 사람이 한다.

## 4-1. 사진-본문 불일치 — 구조로 막는다

**구현 중 실제로 겪었다.** 확인 스크립트가 대시보드에서 사진을 긁어와 카드를 만들었더니
**화재 조사 현장 사진에 공공예식장 안내문**이 붙은 카드가 나왔다. 방송사가 이런 카드를
내보내면 단순 버그가 아니라 신뢰 사고다.

주의로 막을 일이 아니라 **구조로 막는다.**

- 카드 생성의 **공개 진입점은 `draft_id`만 받는다.** 사진 바이트를 밖에서 넘기는
  경로를 공개 API로 두지 않는다.
- 사진은 반드시 **그 초안이 속한 원문의 `press_release_assets`에서만** 가져온다.
- 관리 화면 미리보기에 **원문 링크를 함께 띄워** 사람이 대조할 수 있게 한다.

`cardnews.build_card_images()`는 바이트를 받는 순수 함수라 출처를 알 수 없다.
**출처 보장은 이 함수를 부르는 통합 계층의 책임**이며, 그 계층에 회귀 테스트를 둔다.

## 5. 저장

| 대상 | 위치 | 이유 |
|---|---|---|
| 카드 이미지 | `<디스크>/cardnews/YYYY-MM-DD/<세트>/N.png` | 썸네일 디스크 캐시와 같은 방식. 재기동에도 남는다 |
| 세트 메타 | DB 신규 테이블 `card_news_sets` | 날짜·초안ID·문안·상태(초안/발행)·생성시각 |

보관은 스케줄러 유지보수의 "오래된 카드뉴스 정리" 단계가 맡는다
(`NEWS_SUMMARY_CARDNEWS_KEEP_DAYS`, 기본 30일).

한 장 전환으로 부담이 5분의 1이 됐다. 실제 산출물 6장을 재 보니 사진이 실린 카드가
103~130KB, 글자만 있는 카드가 78~132KB다(PNG `optimize=True`). 지자체 CMS 사진이
이미 압축된 1000px짜리라 밴드에 들어가면 잘 눌린다. 하루 5세트 × 1장 ≈ **0.6MB/일**,
30일 보관해도 20MB 남짓이라 1GB 디스크에 사실상 부담이 없다.

## 6. 화면

| 경로 | 공개 | 내용 |
|---|---|---|
| `/card-news` | **공개** | 오늘의 카드뉴스. 좌우 스와이프, 링크 복사 |
| `/card-news?date=YYYY-MM-DD` | **공개** | 지난 날짜(최근 30일 발행분) |
| `/card-news/manage` | 관리자 | 후보 확정 · 문안 수정 · 재생성 · **다시 그리기** · 발행 · 발행 내리기 · 삭제 |
| `/card-news/<id>/<n>.png` | 발행분만 공개 | 카드 이미지(미발행은 404) |

공개 경로는 기존 `PUBLIC_READ_ENDPOINTS`에 넣는다(보기는 누구나, 변경은 관리자만).

**공개 화면에서 관리 화면으로 가는 길을 낸다.** 상단 메뉴의 "카드뉴스"는 공개
화면으로 가는데 거기에 만들러 가는 링크가 없어, 로그인한 운영자가 주소를 직접 쳐야
했다(2026-08-10 사용자 지적 "카드만들기가 안보여"). 로그인 상태일 때만 보이게
띄운다.

**다시 그리기**는 저장된 문안 그대로 이미지만 다시 합성한다. 배치가 바뀌어도 이미
디스크에 있는 PNG는 안 바뀌므로, 옛 형식(여러 장)으로 만들어 둔 세트를 AI를 다시
부르지 않고 현행 배치로 옮기는 길이 필요하다. 관리 화면은 옛 형식 세트에
"옛 형식 N장" 표시를 띄워 눌러야 할 것을 알려 준다.

**퍼가기**가 핵심이다. 카톡·밴드로 옮겨지는 것이 실제 확산 경로이므로
링크 복사 버튼과 카드 이미지 저장을 반드시 넣는다. OG 태그도 넣어
카톡에 링크를 붙이면 카드가 미리보기로 뜨게 한다.

## 7. 메모리 — 반드시 지킬 것

1080 합성은 썸네일(0.19MB)보다 무겁다. 세 가지를 지킨다.

1. **수집 회차 밖에서 생성**한다 — 회차와 겹치면 피크가 합쳐진다.
2. 합성 직후 **`_release_free_heap()`** 를 부른다(썸네일과 동일).
3. 한 번에 한 세트씩 처리하고, 세트 사이에 결과를 **즉시 디스크로 내린다.**
4. **쓸 만큼만 내려받는다.** 사진을 넘기는 쪽은 제너레이터라 카드가 한 장을 채우면
   거기서 멈춘다. 최대 4장까지는 *시도*하되(저해상도·배너를 걸러내야 하므로) 동시에
   손에 쥐는 것은 한 장이다.
5. 원본은 **카드 폭의 2배(2160px)로 먼저 줄이고** 나서 판정한다. 1억 화소 JPEG는
   RGB로 펼치면 240MB인데 이 서비스는 512MB에서 돈다.

4·5는 한 장 전환 직후 독립 검토에서 잡혔다. 카드는 한 장이 됐는데 받아오는 쪽이
4장을 그대로 쥐고 있어 요청당 최대 165MB였다 — threads 8에 OOM 재시작 이력이 있는
서비스에서 **바꾼 쪽이 아니라 짝이 안 맞게 된 쪽**이 위험해진 사례다.

### 실측 (2026-08-09)

제품 코드 그대로 실제 기사 3건을 만들며 쟀다.

```
세트1  48.8초 · 사진 0장(전부 저해상도 → 텍스트 카드) · 파이썬 힙 +39.1MB
세트2  19.5초 · 사진 2장 · 힙 +44.1MB
세트3  10.7초 · 사진 2장 · 힙 +47.7MB (최고 50.2MB)

세트당 평균 26.3초 — Plan 성공기준 "1분 이내" 충족
```

시간의 대부분은 Gemini 왕복이고 합성은 4초 안쪽이다. 힙은 세트마다 3~5MB씩
늘다 50MB에서 평평해진다 — 세트를 이어 만들어도 계속 쌓이는 형태가 아니다.

## 8. 구현 순서

| 순서 | 내용 | 검증 방법 |
|---|---|---|
| 1 | 카드 합성 모듈 (`cardnews.py`) | 저해상도·사진없음·긴제목 등 경계 입력 단위 테스트 |
| 2 | 문안 생성 액션 + 검증 | 잘못된 반환(장수 초과·빈 문자열) 거절 테스트 |
| 3 | DB 테이블·저장 경로 | 재기동 후에도 카드가 남는지 |
| 4 | 관리 화면 (확정·수정·재생성) | 사람이 실제로 한 세트를 끝까지 만들어 봄 |
| 5 | 공개 화면 + OG 태그 | 카톡에 링크 붙여 미리보기 확인 |
| 6 | 후보 추천 | 하루치로 추천 8건이 납득되는지 눈으로 확인 |

**1번부터 하는 이유** — 가장 불확실한 것이 합성 품질이고, 이미 시안으로 절반
검증됐다. 여기서 막히면 나머지가 의미 없으므로 먼저 끝낸다.

## 9. 하지 않는 것

- 자동 발행 (사람 확인 필수)
- 영상·모션
- 구독자 관리·푸시
- 인스타·밴드 자동 연동 — **이미지 파일을 내려받아 사람이 올린다.** 반응을 보고
  나중에 판단한다
- **첨부 해상도까지 보는 후보 점수** — 아래 §10 참조. 재 보니 순위가 안 바뀐다

## 10. 2026-08-10 개정 — 한 장으로

사용자 지시는 한 줄이었다. "사진 한 장에 기사를 전부 축약해서 넣어 주도록 해줘."

표지 1장 + 본문 N장은 **넘겨야 읽힌다**는 전제 위에 서 있었다. 실제로는 카톡·밴드로
퍼갈 때 첫 장만 옮겨지고 신청 기한·대상이 안 따라갔다. 한 장이면 사진과 요점이
같은 화면에 남는다.

바뀐 것과, 그 때문에 **짝이 안 맞게 된 곳**은 이렇다.

| 바뀐 것 | 짝이 안 맞게 된 곳 | 처리 |
|---|---|---|
| 카드 1장 | 사진을 4장 받아옴 → 요청당 165MB | 제너레이터로 한 장에서 멈춤(§7) |
| 요점을 덜어내 높이를 맞춤 | 소제목과 본문이 별개 블록이라 **본문만 먼저 지워짐** | 요점 단위로 묶어 통째로 덜어냄 |
| 본문 상한 110 → 70 | `image_count`가 `len(cards)+1` 공식 그대로 | 실제 산출 장수를 기록하는 경로로 교체 |
| 배치가 바뀜 | 이미 만든 세트의 PNG는 안 바뀜 | 다시 그리기(§6) |
| 문턱 1080 → 800 | 사진 있는 초안의 43%가 글자만 남던 문제 해소 | §2 |

**독립 검토를 붙이지 않았다면 위 두 줄은 발행 상태 그대로 나갔다.** 자체 검토와
테스트 469건 통과, 시안 육안 확인까지 하고도 못 봤다. 주의가 새로 쓴 코드에 쏠려
있었고, 테스트도 새 경로에 맞춰 같이 고친 것이라 잡지 못했다.

### 문체 — 딱딱하다는 지적

같은 날 "문체가 너무 딱딱한데 조금 부드럽게 글이 이어지게" 지시가 붙었다. 원인은
프롬프트에 있었다 — **소제목을 명사로 끝내라**고 시켜 놓고 문장체를 기대했다.
규칙을 뒤집어 "전부 명사로 끝나면 실패"로 바꾸고, `무슨 일 → 누가 → 언제까지
어떻게` 순으로 앞뒤가 이어지게, `~합니다`체로 쓰게 했다. 어림 표현·자격 한정·
날짜 보간 금지 같은 **사실 보존 규칙은 손대지 않았다** — 부드럽게 만드느라 사실이
흐려지면 안 된다.

### 안 만들기로 한 것 — 해상도를 보는 후보 점수

`card_picks._score()`의 "첨부 있음 +2"는 해상도를 안 본다. 그런데 이 가점이
**운영에서 한 번도 켜진 적이 없었다** — 순위 SQL이 첨부 수를 안 세고 있었다(같은 날
되살렸다). 그래서 "해상도까지 보게 하자"를 재 봤다.

가점을 전부 준 경우와 전부 안 준 경우로 상위 8건을 비교하니 8/07(초안 116건)은
순서까지 같았고, 8/10(48건)은 구성이 같고 한 자리만 밀렸다. **초안의 92~95%가 첨부를
가지고 있어 +2가 상수처럼 작동**하기 때문이다. 컬럼 추가·마이그레이션·백필에
더해 수집 회차마다 첨부 행을 지웠다 다시 넣는 경로까지 손봐야 하는데, 얻는 것이
없다. 실제 처방은 이미 문턱을 800으로 내린 것이었다.
